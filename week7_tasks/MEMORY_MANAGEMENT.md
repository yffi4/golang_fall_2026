# Week 7. Memory Management в Go

## 1. Stack и heap

Каждая программа на Go использует два вида памяти.

|            | Stack                                  | Heap                                      |
|------------|-----------------------------------------|---------------------------------------------|
| Кому принадлежит | одной goroutine                   | всей программе                              |
| Allocation | сдвиг указателя — почти бесплатно       | поиск свободного места — требует времени    |
| Freeing    | автоматически, при возврате из функции  | garbage collector (GC), позже               |
| Размер     | начинается маленьким, растёт копированием (до 1 GB на 64-bit) | столько, сколько даст машина |
| Хорошо для | локальных, короткоживущих значений      | значений, которые живут дольше своей функции или являются shared |

Важный момент: **вы никогда не выбираете stack или heap сами**. `new(T)`, `&T{}` и `make` не означают "heap" — решение принимает компилятор (**escape analysis**), и в спецификации языка слова "stack"/"heap" вообще не упоминаются.

### Почему `&u` безопасен, если `u` — локальная переменная

В C возврат адреса локальной переменной — классический "dangling pointer" баг: стек-фрейм исчезает, а указатель остаётся висеть. В Go это безопасно, потому что если компилятор видит, что `&u` "уходит" из функции (shared up), он просто кладёт `u` на heap вместо stack — тогда никакого dangling pointer не возникает, память живёт столько, сколько на неё есть ссылки.

### Goroutine stack растёт и копируется

Goroutine стартует с крошечным stack (несколько KB). Когда не хватает места, runtime выделяет новый, больший stack и **копирует** туда весь старый — это возможно только потому, что компилятор знает тип каждого stack frame: при копировании runtime проходит по фреймам с этой типовой информацией и переписывает все указатели, которые указывали *внутрь старого стека*, на соответствующие адреса в новом. Указатели в heap не трогаются (heap не двигается). Именно поэтому это безопасно, даже если какие-то указатели указывают внутрь стека.

Но у этого роста есть предел — 1 GB на 64-bit системе. Превысили — `fatal error: stack overflow`.

**Практическая находка.** Мы измерили реальный frame size через `go build -gcflags=-S`:
- `depth` с `pad [64]byte` → frame **96 bytes** → `depth(1_000_000)` работает (~96 MB stack).
- та же функция с `pad [1024]byte` → frame **1056 bytes** → `1056 * 1_000_000 ≈ 1.056 GB` — это **больше** лимита в 1 GB, и программа реально падает с `fatal error: stack overflow`. То есть простое увеличение локального массива превращает рабочую программу в stack overflow с той же логикой рекурсии.
- Убрали строку, которая *читает* `pad` (оставили только запись) — frame **уменьшился с 96 до 32 bytes**: запись сама по себе не даёт компилятору выбросить массив, но без чтения назад компилятор упрощает layout фрейма.

**`fatal error: stack overflow` — это не panic.** `recover()` его не перехватывает: deferred-функция с `recover()` не успевает выполниться, потому что в этот момент может не быть места даже на то, чтобы её запустить. Runtime считает stack overflow (как и out-of-memory, concurrent map misuse) неустранимой ошибкой, а не panic.

## 2. Escape analysis

Escape analysis — это часть компилятора, которая решает: может ли значение остаться в stack frame функции, или оно может понадобиться после того, как функция вернётся. Если да — значение **escapes** на heap.

```
go build -gcflags='-m' .        # короткий отчёт
go build -gcflags='-m -l' .     # -l отключает inlining — легче читать
go build -gcflags='-m -m -l' .  # ещё и объясняет, ПОЧЕМУ
```

| Сообщение | Значение |
|---|---|
| `moved to heap: u` | сама переменная `u` живёт на heap |
| `... escapes to heap` | значение (`make`, литерал, значение, boxed в interface) выделяется на heap |
| `does not escape` | остаётся на stack |
| `leaking param: p` | указатель `p` сохраняется или возвращается — то, что передаёт caller, может оказаться на heap |
| нет строки вовсе | ничего выделять не нужно — функция вернула копию |

### Четыре (на самом деле больше) причины escape

1. **Sharing up** — возврат указателя на локальную переменную (`return &u`).
2. **Хранение где-то, что живёт дольше** — глобальная переменная, map, slice/channel, которые сами escape.
3. **Interfaces** — передача значения как `any`/`interface` обычно boxing'ует его на heap (`fmt.Println(x)` заставляет `x` escape).
4. **Closures**, которые переживают функцию, захватывают переменные на heap.
5. **Размер** — слишком большое для stack (в Go 1.24: `make` > 64 KB, локальные переменные > 128 KB), либо размер неизвестен на этапе компиляции (`make([]byte, n)`).

**Практическая находка про версии компилятора.** В задаче с функциями `f1..f10` мы предсказали, что `make([]int, n)` (размер не константа) будет escape — и в Go 1.24 (как в примере лекции с `dynamicSize`) это действительно так. Но на **go1.27.1**, на котором мы реально собирали код, компилятор сообщает **`does not escape`** для той же самой строки! Это буквально предупреждение из PDF: "Go 1.25 и 1.26 научились оставлять на стеке больше слайсов с неконстантным размером." Вывод: никогда не полагайтесь на то, что значение останется на stack — измеряйте, а не предполагайте, и это может зависеть от версии компилятора.

Другая находка — **размер лимита измерен точно**: бинарным поиском по `make([]int, N)` в функции `sum()` мы нашли, что `N=8192` → `does not escape`, а `N=8193` → `escapes to heap`. `8192 * 8 bytes = 65536 bytes = 64 KB` — ровно та граница, которая указана в лекции (int — 8 байт на 64-bit). Причина лимита: stack frame должен оставаться маленьким и предсказуемым, потому что рост/копирование стека (см. раздел 1) должно быть дешёвым — если бы в stack можно было класть произвольно большие локальные массивы, один вызов функции мог бы разрастить весь стек goroutine.

## 3. Allocations: почему они дорогие и как их считать

**Каждая heap allocation стоит дважды**: один раз при выделении, второй раз — когда GC её находит и освобождает. Меньше allocations → меньше работы для GC → быстрее программа.

Три способа посчитать allocations:
1. В бенчмарке: `go test -bench=. -benchmem` (колонки `B/op`, `allocs/op`).
2. В тесте: `testing.AllocsPerRun(1000, func() { ... })`.
3. В работающей программе: `runtime.ReadMemStats(&m)` → `m.HeapAlloc`, `m.Mallocs`, `m.NumGC`.

### Типичные источники allocations и фиксы

| Паттерн | Почему allocates | Фикс |
|---|---|---|
| `return &Point{x, y}` для маленькой структуры | структура escapes | вернуть значение: `Point{x, y}` |
| `s += x` в цикле | новая строка каждый раз (строки неизменяемы) | `strings.Builder` + `Grow` |
| `append` без capacity | массив реаллоцируется по мере роста | `make([]T, 0, n)` |
| `fmt.Sprint(n)` / передача в `any` | boxing + форматирование | `strconv.AppendInt`, конкретные типы |
| новый буфер на каждый запрос | allocation на каждый вызов | переиспользовать, например `sync.Pool` |
| конвертации `[]byte` ↔ `string` | каждая конвертация копирует | оставаться в одном типе (пакет `bytes`) |

**Измерено реально** (`JoinIDsSlow` vs `JoinIDsFast`, 10 ids, `go test -bench=. -benchmem`, Apple M5 Pro):

```
BenchmarkJoinIDsSlow   384.8 ns/op   232 B/op   18 allocs/op
BenchmarkJoinIDsFast    66.7 ns/op    80 B/op    1 allocs/op
```

`JoinIDsSlow` делает allocation на каждой итерации: `escape analysis` показывает `id escapes to heap` на строке с `fmt.Sprint(id)` — `Sprint(a ...any)` boxing'ует `id` в interface, плюс `s += ...` каждый раз реаллоцирует строку (строки immutable). `JoinIDsFast` делает **ровно одну** allocation — это `strings.Builder`-буфер, выделяемый при первом росте; избежать её нельзя, если вы хотите вернуть полностью владеемую `string`.

**Про value vs pointer** (`NewPointValue` vs `NewPointPointer`, с `//go:noinline`, чтобы inlining не "спрятал" escape-решение внутри цикла бенчмарка):

```
NewPointValue       0.45 ns/op      0 B/op   0 allocs/op
NewPointPointer     5.47 ns/op     16 B/op   1 allocs/op
```

Возврат значения (не указателя) из маленькой структуры — бесплатно: нет строки escape вообще. Возврат `&Point{...}` — классический `escapes to heap` (как `newUserPointer` в лекции).

**Про capacity** (`CollectNoCap` vs `CollectWithCap`, n=1000):

```
CollectNoCap(1000)    2074 ns/op   25208 B/op   12 allocs/op
CollectWithCap(1000)   922 ns/op    8192 B/op    1 allocs/op
```

1000 `int` по 8 байт — это всего 8000 байт, а `CollectNoCap` тратит **25 KB**. Разница — это все промежуточные массивы, которые `append` выделял и бросал по пути роста capacity (примерно `1,2,4,8,...,1024` — именно 12 реаллокаций), пока растил slice от `nil`. Каждый из них потом должен собрать GC — ровно иллюстрация правила "allocation стоит дважды".

**Осторожно: не оптимизируйте бездумно.** Возврат значения вместо указателя хорош для маленькой структуры; для большой структуры копирование может стоить дороже, чем allocation. Всегда измеряйте бенчмарком до и после.

## 4. Garbage collection: основы

GC освобождает heap-память, на которую больше нет ссылок. Значение **reachable**, если до него можно дойти от **root** (stack goroutine, глобальная переменная) по цепочке указателей. Всё остальное — garbage.

Как работает Go GC:
- **Mark and sweep.** Сначала GC помечает все reachable объекты, потом sweep — освобождает всё, что не помечено.
- **Concurrent.** Большая часть работы идёт параллельно с программой на других ядрах; ваши goroutines останавливаются только на очень короткие "stop-the-world" паузы (обычно меньше миллисекунды).
- **Non-moving.** Объекты не двигаются по адресам — heap не компактифицируется.
- **Write barrier.** Пока идёт marking, программа продолжает менять указатели; небольшой кусок кода на каждой записи указателя гарантирует, что GC не потеряет reachable объект.

**Green Tea (Go 1.26+)** — новый default collector, использующий те же идеи (reachability, GOGC), но marking теперь обходит целые страницы маленьких объектов вместо прыжков от объекта к объекту — это дружелюбнее к CPU-кэшу, команда Go сообщает о 10–40% меньше overhead в GC-heavy программах.

### Когда GC запускается — GOGC

```
heap goal ≈ live heap × (1 + GOGC/100)
```

С `GOGC=100` (default) GC запускается, когда heap удвоился с прошлого цикла.

### `GODEBUG=gctrace=1` — как читать строку

Реальная строка из нашего прогона (`GOGC=100`):

```
gc 115 @0.514s 0%: 0.008+0.39+0.014 ms clock, ..., 47->48->24 MB, 49 MB goal, 0 MB stacks, 0 MB globals, 15 P
```

| Часть | Значение |
|---|---|
| `gc 115` | 115-й цикл GC с момента старта программы |
| `@0.514s` | время с момента старта программы |
| `0%` | накопленный % CPU-времени, потраченного на GC |
| `0.008+0.39+0.014 ms clock` | stop-the-world пауза + concurrent mark + stop-the-world пауза |
| `47->48->24 MB` | heap в начале GC → heap к концу marking (может расти, пока marking идёт параллельно) → live heap после sweep |
| `49 MB goal` | цель для следующего цикла: `24 MB × (1 + 100/100) = 48 MB` |
| `0 MB stacks, 0 MB globals` | дополнительная память, посчитанная от стеков goroutine / глобальных переменных |
| `15 P` | сколько логических процессоров использовал этот цикл GC |

### Trade-off: память vs CPU — что мы реально измерили

Программа: ~22 MB живых данных (`live`, 80 000 `*Record`), ~2.7 GB мусора, прогоняемого через второй цикл (10 000 000 `*Record`, живущих одну итерацию).

**Важная деталь, которую мы обнаружили сами:** в первой версии кода `consume(r *Record) int { return r.ID }` **не заставляет `r` escape** — escape analysis на go1.27.1 честно пишет `r does not escape`, потому что указатель никуда не сохраняется и не возвращается. Из-за этого второй цикл вообще не создавал мусор на heap, и `GOGC` почти не влиял на результат. Пришлось сознательно заставить объект escape — через запись в глобальную переменную (`discard = &Record{...}`), что по лекции и есть классический "leaking param"-паттерн. Это сам по себе хороший пример того, что написано в Warning-блоке: не предполагайте escape, измеряйте — то, что выглядит как "мусор после одного использования", компилятор вполне может доказать безопасным для stack.

После фикса (Apple M5 Pro, 15 CPU, go1.27.1):

| GOGC | GC cycles | heap from OS | total pause |
|---|---|---|---|
| 50 | 236 | 50 MB | 3.9 ms |
| 100 (default) | 118 | 65 MB | 2.4 ms |
| 200 | 59 | 87 MB | 1.1 ms |
| 400 | 30 | 144 MB | 0.6 ms |
| off | 0 | 2894 MB | 0 ms |
| off + `GOMEMLIMIT=100MiB` | 45 | 103 MB | 1.6 ms |

Форма результата совпадает с лекцией: меньше `GOGC` → больше циклов GC, меньше памяти, больше суммарного времени пауз; `GOGC=off` никогда не собирает мусор, и heap растёт до полного объёма (~2.7 GB); `GOGC=off` с `GOMEMLIMIT` снова ограничивает heap, но триггером теперь служит память, а не доля роста.

**Но wall-clock время дало неожиданный результат.** На этой машине (много RAM, 15 ядер) три повторных замера показали, что **`GOGC=off` оказался быстрее** (~0.40 s), чем `GOGC=100` (~0.52 s) — то есть противоположно табличке из лекции, где "`off`" был самым медленным. Причина: "нет GC" не значит "нет стоимости" — каждый из 10 000 000 объектов всё равно выделяется нормально, просто никогда не освобождается, и heap растёт до ~2.7 GB. На машине с достаточным количеством RAM и быстрым многоядерным concurrent marker-ом плата за частые, но дешёвые GC-циклы (`GOGC=100`) оказалась *больше*, чем просто дать allocator'у работать свободно. Утверждение лекции справедливо именно в ситуации, для которой оно написано: когда рост до ~2.7 GB создаёт реальное давление на память — paging, swapping, или упор в лимит контейнера. В такой среде `GOGC=off` проигрывает сильно — именно поэтому существует `GOMEMLIMIT`: он защищает от этого сценария, не теряя низкий CPU-overhead `GOGC=off`, когда память реально не является проблемой. Хороший пример того, что правильный выбор зависит от workload и машины, а не является универсальным рейтингом.

### Настройки GC

| Настройка | Что делает |
|---|---|
| `GOGC=100` (env) / `debug.SetGCPercent(100)` | насколько heap может вырасти перед следующим циклом |
| `GOGC=off` | нет GC по росту heap (опасно само по себе!) |
| `GOMEMLIMIT=500MiB` / `debug.SetMemoryLimit(...)` | soft limit: когда память приближается к нему, GC запускается чаще (Go 1.19+) |
| `runtime.GC()` | форсирует полный сбор прямо сейчас — полезно в тестах/демо, редко в реальном коде |

**Совет.** В контейнерах (Docker, Kubernetes) ставьте `GOMEMLIMIT` чуть ниже лимита контейнера (например, 90%) — тогда GC будет работать усерднее до того, как контейнер убьют за превышение памяти.

**Какой `GOGC` выбрать:**
- Сервис с малым количеством памяти: меньший `GOGC` (50–100), или лучше — фиксированный `GOMEMLIMIT` чуть ниже лимита контейнера: предсказуемость памяти важнее, чем CPU, а `GOMEMLIMIT` реагирует прямо на давление по памяти.
- Batch job на большом сервере: больший `GOGC` (200–400) или даже `off`, если задача короткоживущая и памяти много — обмен памяти на меньшее число более дешёвых циклов GC минимизирует общее время работы, когда нет жёсткого потолка по памяти.

## 5. "GC освободит это за меня" — не всегда

GC освобождает **только недостижимую** память. Если вы держите указатель на что-то большое, оно останется живым — даже если вам нужен лишь крошечный кусочек.

**Классический memory leak**: slice header — это `{pointer, len, cap}`. `data[:11]` получает *новый* header с `len=11`, но указатель всё равно смотрит на тот же backing array, что и исходный `data` (1 MB). GC не знает, что "этому slice нужны только первые 11 байт" — он видит только, что указатель указывает куда-то внутрь массива, значит весь массив reachable, пока хоть один slice в него указывает. То же самое со строками: `big[:5]` делит backing array с `big`.

**Измерено реально** (100 "файлов" по 1 MB каждый, `runtime.GC()` + `runtime.ReadMemStats`):

```
subslices:   100 MB   # 100 заголовков по 11 байт держат живыми 100 массивов по 1 MB
copies:        0 MB   # bytes.Clone(data[:11])
substrings:  100 MB   # big[:5] от 1 MB строки
clones:        0 MB   # strings.Clone(big[:5])
```

Числа совпали с лекцией точно. Фикс — `bytes.Clone()` / `strings.Clone()`: копирует только нужные байты в новую, маленькую allocation, и позволяет большому массиву/строке стать мусором немедленно.

**Подвох при измерении**: если измерить heap сразу после создания "утечки", но переменная больше не используется дальше по коду, компилятор/runtime может доказать, что она уже недостижима, и GC её соберёт *раньше* измерения — вы увидите обманчивые 0 MB. `runtime.KeepAlive(x)` после измерения заставляет runtime считать `x` reachable до этой точки, и тогда замер честный.

## 6. `sync.Pool` — переиспользование буферов

`sync.Pool` хранит объекты, которые можно переиспользовать, вместо того, чтобы allocate новый каждый раз. GC может опустошить пул в любой момент — это **cache, а не storage**.

**Измерено реально** (`RenderNew` — новый 4 KB buffer каждый вызов, `RenderPool` — буфер из пула, 200 ids, `go test -bench=. -benchmem`):

```
BenchmarkRenderNew    4946 ns/op   4146 B/op   2 allocs/op
BenchmarkRenderPool   4631 ns/op      0 B/op   0 allocs/op
```

`RenderNew` allocates новый `*bytes.Buffer` + его backing `[]byte` на каждый вызов (2 allocations), хотя буфер выбрасывается через несколько строк. `RenderPool` в steady state делает **0 allocations** — `Get` просто возвращает уже выделенный объект.

- **Зачем `buf.Reset()` после `Get`?** `sync.Pool` не знает и не заботится, в каком состоянии объект, когда вы делаете `Put` — он просто отдаёт тот же объект следующему `Get`, байт в байт как он был оставлен. Без `Reset()` новые данные просто дописались бы после старых вместо начала "с чистого листа".
- **Что сломается, если продолжать использовать `buf` после `Put`?** С момента `Put` вы больше не владеете этим буфером — любой другой `Get` может в любой момент получить тот же самый указатель. Если вы продолжаете писать/читать `buf` после `Put`, у вас классический data race: два goroutine мутируют один `*bytes.Buffer` без синхронизации.

## Ключевые выводы

- Stack — per-goroutine, быстрый и освобождается автоматически. Heap — shared, его чистит GC.
- Вы не выбираете stack или heap — это делает escape analysis компилятора. Смотрите на это через `-gcflags=-m`, но помните, что ответ может отличаться между версиями компилятора (мы это увидели вживую на `make([]int, n)` и на `depthBig`).
- Sharing down обычно остаётся на stack; sharing up, interfaces, closures и большие/неизвестные размеры — escape.
- Каждая heap allocation стоит дважды: при выделении и при сборке. Измеряйте через `-benchmem` и `testing.AllocsPerRun`.
- Go GC — concurrent mark-and-sweep коллектор. Он освобождает только недостижимую память.
- `GOGC` обменивает память на CPU; `GOMEMLIMIT` задаёт soft memory limit. Правильный выбор — не универсальный, а зависит от workload и машины (мы это увидели на `GOGC=off`, который оказался быстрее на нашей машине, хотя теория говорит об обратном в условиях реального memory pressure).
- Маленький subslice или substring может держать живым огромный массив — клонируйте через `bytes.Clone` / `strings.Clone`.

## Вопросы для защиты (с короткими ответами)

1. **Разница между stack и heap? Какой быстрее и почему?** Stack — per-goroutine память, allocation — это просто сдвиг указателя, freeing автоматический при возврате из функции; heap — shared память всей программы, allocation требует поиска свободного места, freeing делает GC позже. Stack быстрее, потому что нет поиска свободного места и нет работы GC.
2. **Кто решает, на stack или на heap переменная? `new`/`&` решают это?** Решает компилятор через escape analysis. `new(T)`, `&T{}`, `make` сами по себе не означают heap — это зависит от того, "убегает" ли значение из функции.
3. **Что такое escape analysis? Назвать причины escape.** Часть компилятора, решающая, может ли значение остаться в stack frame функции. Причины: sharing up (возврат указателя на локальную переменную), хранение в глобальной/map/slice/channel, которые живут дольше, boxing в interface, closures, переживающие функцию, и слишком большой/неизвестный размер.
4. **Как посмотреть результат escape analysis? Что значит `leaking param`?** `go build -gcflags='-m -l'`. `leaking param: p` значит, что указатель `p` сохраняется или возвращается внутри функции, поэтому то, что передаёт caller, может оказаться на heap.
5. **Как считать allocations в тесте и в бенчмарке?** В тесте — `testing.AllocsPerRun(n, func(){...})`. В бенчмарке — флаг `-benchmem` у `go test -bench=.`, колонки `B/op`/`allocs/op`.
6. **Как GC решает, что освобождать? Что такое roots?** GC помечает всё reachable от roots (стеки goroutine, глобальные переменные) по цепочке указателей, затем освобождает всё непомеченное (mark and sweep).
7. **Что контролируют `GOGC` и `GOMEMLIMIT`?** `GOGC` — насколько heap может вырасти относительно live heap перед следующим циклом GC (`heap goal ≈ live heap × (1+GOGC/100)`). `GOMEMLIMIT` — soft-лимит по абсолютной памяти, при приближении к которому GC запускается чаще, независимо от `GOGC`.
8. **Почему маленький slice или substring может держать живой много памяти?** Slice header — `{pointer, len, cap}`; `data[:11]` получает свой header, но указывает на тот же backing array, что и оригинал. GC видит только, что массив reachable через указатель, и не знает, что реально используется лишь малая часть — поэтому весь массив остаётся живым, пока хоть один slice/string в него указывает.
